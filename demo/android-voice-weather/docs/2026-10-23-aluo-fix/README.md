独立声音唤醒已修复，保留 Vosk 原文；更新后的主 APK 已安装到设备。原生正负样本、PCM 模拟流程、回声保护及外部扬声器到真实麦克风的模拟天气流程分别通过。另一次同机扬声器回采仍出现命令后半句丢词，保留失败记录，不宣称所有声学场景通过。

用户随后要求办公区不要修改电脑或手机音量。已移除电脑脚本的调音量参数及手机测试中的 `setStreamVolume`，只读确认电脑为原来的 6%、手机媒体为原来的 40/150；之后未再运行有声测试。最后仅重新构建、运行单元测试和 Lint。以下有声证据来自这条约束提出之前，不能当作在当前低音量下的复测。

## 问题与实现

原先把无约束 Vosk 转写的“阿洛”文本前缀作为声音唤醒依据。两条合成音频被转写为“那 咯”“落 上海 明天 天气 怎么样”，因此即使后续文字流程正常，声音入口也无法唤醒。初次失败和旧版页面验证保留在相邻的 `2026-10-23-aluo-device/`，不覆盖历史证据。

本次让同一份 16kHz PCM 同时进入两个独立解码器，共享已有的只读中文模型：

1. 原始转写解码器仍无词表限制，partial、最终文字、界面和原文日志不做错词替换。开启原生词时间输出，用于定位命令边界。
2. 独立唤醒解码器采用 `阿 洛` 与 `[unk]`，允许其他语音返回未知结果，结合每词置信度、时长和位置检查，避免把任意语音都当作唤醒词。它提供独立的声学命中证据，不替换转写文本。
3. 只接受开头连续的“阿”“洛”，每词置信度至少 0.85、总长 0.12–1.2 秒、词间间隔不超过 0.2 秒；前面已有原始讲话或未知词时不唤醒。该置信度是限定词表下的解码指标，不表示真实准确率。
4. 两个解码器使用同源的绝对词时间，将唤醒音节之后的原始词交给 Qwen。声音检测明确拒绝时不回退到原始文本前缀；文字模拟仍按显式称呼进入。播报重叠、会话失效与确认窗口检查优先于命中证据。
5. 正常句末与 20 秒强制分段都会收尾唤醒检测；停止时的尾句仍只记录。原有 WAV 保存与上传空实现保持不变。

Vosk `reset()` 不会使词时间回到零。首轮连续长流测试发现重复叠加片段偏移导致漏检，已改为直接对齐两个解码器的绝对时间，并保留首轮失败文件 `acoustic-first-attempt.json`。

还实测比较了包含“安诺”等竞争短语的词表：直输入正负样本通过，但设备再录音后，竞争词表把真实“阿洛”音频解为“阿 诺”，词置信度约 0.51，导致漏检。相同采音在 `阿 洛 + [unk]` 词表下得到两个置信度均为 1 的唤醒音节；真正“安诺”的负样本在该词表下首词置信度约 0.58，低于 0.85 接受阈值。最终移除这些竞争短语，并重新回归正负样本及真实麦克风流程。对比见 `speaker-grammar-comparison.json`；它是测试音频的解码指标，不是对真实概率的估计。

外部声源测试起初在电脑原输出音量 6% 下未采到任何命令转写，保留 `external-speaker-instrumentation.txt`。随后在 40% 下通过，保留 `external-speaker-volume40-instrumentation.txt`；结束恢复 6%。同机路径与外部路径不同，以上对比不能直接证明丢词的硬件或音频处理根因。

真实麦克风闭环日志还记录了助手自己的“收到”、确认询问和天气播报被再次采入，均因播报重叠而只记录。真实天气请求计数为 0，未执行录音上传。

## 验证边界

正负样本来自 macOS Tingting 离线合成，位于测试 APK 的 `assets/wake/`，不是多说话人或真人准确率测评。未知环境噪声、不同口音、远场、电机噪声、长时间运行和树莓派性能仍需单独验证。

不采用“那咯、安诺”等原始转写别名直接唤醒。声学层仍可能把相似发音误认为“阿洛”；当前阈值和小规模负样本不能证明所有近音都不会误触发。额外解码器增加 CPU 与内存占用，不能把手机验证外推为低性能设备实时性保证。
