# ARMv7 预热后真实麦克风验证

日期：2026-10-27，Asia/Shanghai。最终版本：0.2.2（versionCode 4）。

## 结论

已完成独立 board 模块的单识别器预热、真实麦克风采集、连续解码、丢帧计数、内存采样和前台生命周期控制。最终 120 秒实际采集与解码样本相等，应用队列丢帧为 0、读取错误为 0，后台停止检查通过；但真人语音没有产生任何临时转写或完整句，因此不能声称连续语音识别功能通过，也不能用本轮以低能量输入为主的 RTF 代替连续讲话性能。

手机版 app 目录、构建配置和原生实现保持不变。79 个原手机文件在本轮实现后保存的哈希与最终复核一致，构建任务仅针对 board；哈希统计不包括构建产物。

## 实现范围

- `MainActivity.java`：麦克风授权、音源/输入设备选择、120 秒启动与停止、临时和完整文字显示；只在前台录音，离开页面即停止。
- `MicSession.java`：一个模型、一个识别器；先用原固定 PCM 预热两轮、final/reset，之后才创建并启动 AudioRecord。预热输出不进入真实识别结果。
- 16kHz、单声道、PCM16，每帧最多 1280 采样（80ms）；录音缓冲至少 2秒。高优先级采集线程和解码线程分离，队列最多32帧；队列满丢新帧并记录精确采样数。
- 帧带累计采样序号；出现应用丢帧后，后续解码遇到序号不连续就 reset，避免拼接断开的音频。该分支有实现，但最终零丢帧运行没有触发，未另外注入故障验证。
- 每20秒已解码音频 final/reset 一次；自然空端点不会推迟该保护，结果按 `natural`、`segment_limit`、`stop_tail` 区分。保护可能切在句中，当前没有语义执行。
- 每秒采样进程 PSS/RSS/VmSwap/原生堆；硬件时间戳、采样量与墙钟差异、队列深度与等待、解码时间、音量等写入诊断报告。约5秒更新一次，结束时原子保存。
- 新增 RECORD_AUDIO 权限，没有 INTERNET 权限，没有 Qwen、天气调用、TTS 或自动外放；不保存原始 PCM/WAV，只在本地保存识别文字和指标。

## 开发板与实际通路

沿用前轮同一块 iot_imx7d_pico，Android Things 1.0.15 / Android 8.1 / API 27 / ARMv7；Vosk 0.3.75、JNA 5.18.1、small-cn-0.22。

用户确认：已说过测试句，麦克风插在3.5mm口，插头有三道黑环（四段 TRRS）。官方资料说明该型号采用 CTIA 接法的3.5mm耳麦口；四段外形仍不能确认附件就是 CTIA，也不能证明麦克风本身有效。[TechNexion 官方规格](https://www.technexion.com/wp-content/uploads/2022/09/product-brief_pico-pi-imx7.pdf)

实际 Android 输入为 id=4、type=15，AUX Input → I²S1；`/proc/asound` 显示 card0 capture 关闭，card1 SGTL5000 capture 打开，S16_LE、48kHz、双声道。AudioFlinger 对应用提供16kHz录音，再转换成请求的单声道。说明应用确实打开了板上模拟音频输入路径，不能据此证明插头、增益、模拟信号与重采样后的语音质量正确。

## 实测结果

三次均为真实 AudioRecord 输入；预热结束后没有将合成 PCM 注入实时解码器。

| 运行 | 时长 | 采集/解码样本 | 应用丢弃 | 最大队列 | 最大排队等待 | 平均解码 RTF | 采样最大 PSS |
|---|---:|---:|---:|---:|---:|---:|---:|
| 0.2.0，无长段保护 | 120.042秒 | 1920000 / 1817600 | 102400（6.4秒） | 32帧 | 5224ms | 0.911 | 152.53 MiB |
| 0.2.1，自然端点会推迟保护 | 120.040秒 | 1920000 / 1920000 | 0 | 26帧 | 2008ms | 0.867 | 156.63 MiB |
| **0.2.2，每20秒强制保护** | **120.035秒** | **1920000 / 1920000** | **0** | **14帧** | **1057ms** | **0.673** | **150.54 MiB** |

0.2.0 的仪器测试因应用队列丢样本而失败，原始报告保留。0.2.1 虽通过采集断言，但保护触发次数为0，存在空自然端点持续推迟保护的问题，且积压已接近录音缓冲时长。0.2.2 将重置计时与自然端点分开，最终触发6次保护、没有序号断开。各轮输入和系统状态不同，以上不是严格控制变量实验，不能把改善全部归因于单一修改。

最终运行补充数据：

- 读取错误0、零长度读取0；最大读取完成间隔108ms。
- 采集120秒PCM，墙钟120.035秒，差异-35ms。
- 最大单帧解码约864ms；该值不含单独的 final/reset 刷新操作，完整阻塞效果另体现在队列等待中。平均RTF低于1不代表每帧都能在80ms内处理。
- 116次硬件时间戳成功，0次失败；首尾硬件帧位置跨度相对已读采样跨度差-128采样（-8ms）。该差异包含采样点和流水线缓冲因素，不能据此保证底层绝对无丢音。
- 采样最大RSS约172.27 MiB。PSS为整个进程采样，含仪器测试/UI等开销，不是纯模型内存或精确峰值。
- 监听前20个内存采样的平均PSS约148.76 MiB，后20个约146.50 MiB；本轮没有明显上升趋势，不能替代长时间泄漏检查。
- 两轮预热分别约12.140秒、1.665秒（每轮音频2.09025秒）；只有预热完成后才录音。
- 临时文字更新0、自然完整句0、强制完整文字0。峰值18697、RMS≥350的帧25个（约2秒），大部分时间输入能量低。短时较大信号不能证明有效人声或识别准确率。

## 风险与下一步

连续采集与解码通路在最终这120秒通过了应用侧检查；真人连续识别没有通过。仍需用已知可用的CTIA耳麦或其他已知有效输入，核对麦克风偏置/增益、CTIA/OMTP及插接、电气信号质量，并验证实际输入包含清晰人声。不能只放大噪声来宣称问题已解决。若要直接试听或分析波形，需要单独启用有限时长的本地音频诊断；本版没有保存音频。

有清晰人声后，仍需多句连续讲话、句末切分、不同城市/距离/噪声、长于120秒稳定性，以及真正底层丢音检测。未测试MIC音源、指定其他输入设备的实际效果、拒绝授权、切换设备和故障恢复，不承诺所有硬件组合可用。
